# AI辅助形式化验证：从代码到证明的自动化管道

> **来源映射**: [07-总览] → AI增强形式化方法 → 自动化验证管道

> **定位**：AI正在进入形式化验证领域——从自动生成规范到辅助证明构造。虽然当前能力有限，但"AI生成候选 + 机器验证"的管道代表了软件可靠性工程的下一个前沿。
>
> **核心命题**：形式化验证的最大瓶颈不是计算能力，而是人工编写规范和证明的智力成本。AI可能降低这个门槛，但不会消除对人类专家的需求。

---

## 一、思维导图：AI辅助验证管道

```text
AI辅助形式化验证
│
├─【阶段1：规范生成】
│   ├─ 从自然语言需求生成TLA+/Coq规范
│   ├─ 从代码提取不变量候选
│   └─ 人类Review和修正
│
├─【阶段2：证明辅助】
│   ├─ LLM建议证明策略（tactics）
│   ├─ 自动引理生成
│   └─ 反例解释和修复建议
│
├─【阶段3：验证执行】
│   ├─ 模型检查器（TLC, UPPAAL）
│   ├─ 定理证明器（Coq, Isabelle, Lean）
│   └─ SMT求解器（Z3, CVC5）
│
├─【阶段4：反馈迭代】
│   ├─ 验证失败 → 反例分析
│   ├─ LLM解释失败原因
│   └─ 生成修复建议
│
└─【当前局限】
    ├─ LLM生成规范准确率：30-50%
    ├─ 复杂不变量仍需人工
    └─ 证明策略建议质量不稳定
```

## 二、AI时代的形式化验证范式

> **核心命题**：2025-2026年，AI与形式化验证的融合已从"辅助工具"演进为"范式转移"。从Microsoft Research提出的Intent Formalization到端到端可验证代码生成流水线，形式化验证正在从学术象牙塔走向工业主流。

---

### 2.1 意图形式化：弥合意图鸿沟

**定义**：意图形式化（Intent Formalization）是指将非正式的自然语言需求转化为可被机器检查的形式化规范的系统化过程，其核心挑战是消除"意图鸿沟"（Intent Gap）——即人类真实意图与AI生成代码之间的语义偏差。

**机制**：**Microsoft Research** (2026年3月)提出的框架将意图形式化分为三个层次：

| 层次 | 名称 | 机制 | 保证级别 | 适用场景 |
|------|------|------|---------|---------|
| **L1** | 轻量化测试 | 从自然语言生成单元测试和属性基测试 | 统计置信 | 快速原型、低风险模块 |
| **L2** | 全功能规范 | 将需求翻译为TLA+、Dafny或Verus等形式化规约 | 数学保证 | 分布式协议、安全关键组件 |
| **L3** | DSL自动综合 | AI根据自然语言描述自动生成领域特定语言及其语义 | 端到端保证 | 标准化协议、重复性领域 |

**案例**：在Azure Cosmos DB的分布式事务协议验证中，研究团队使用LLM将RFC文档中的散文描述翻译为TLA+规约初稿，人类架构师仅需修正边界条件，规约编写效率提升约5倍。

> **Microsoft Research** (2026): "Intent Formalization: A Grand Challenge for Reliable Coding in the Age of AI Agents", *MSR Technical Report*.

**批判性分析**：意图形式化的最大局限在于"元意图"问题——当需求本身模糊或自相矛盾时，形式化过程会暴露而非解决这种模糊性。此外，当前LLM在处理跨域依赖（如安全需求与性能需求的冲突）时仍表现脆弱，L3级DSL自动综合在工业场景中尚处实验阶段。该框架隐含假设了需求可以被分层分解，但对于紧耦合系统，这种分解本身可能就是最大的挑战。

---

### 2.2 AI使形式化验证成为主流：Kleppmann预测

**定义**：系统思想家**Martin Kleppmann**（《Designing Data-Intensive Applications》作者）在2025年12月提出的系统性预测：AI将触发形式化验证从"学术奢侈品"到"工业必需品"的范式转移。

**核心论点**：

| 论点 | 论据 | 工程含义 |
|------|------|---------|
| **成本指数级下降** | AI辅助写证明，将形式化验证的人力成本降低1-2个数量级 | 中型团队可负担关键组件的形式化验证 |
| **替代人工审查** | AI生成代码的可靠性无法通过传统代码审查保证 | 形式验证成为AI代码质量的唯一确定性保障 |
| **精确性对冲概率性** | 形式验证的数学精确性对冲LLM的概率性不精确性 | 形成"AI生成 + 形式验证"的互补架构 |

**案例数据对比**：

```
┌──────────────────────────────────────────────────────────────────┐
│  形式化验证成本对比：传统 vs AI时代                                 │
├──────────────────────────────────────────────────────────────────┤
│  项目: seL4微内核形式化验证 (Klein et al., 2009)                   │
│  ├─ 规模: 8,700行C代码                                            │
│  ├─ 投入: 20人年                                                   │
│  ├─ 证明代码: 200,000行Isabelle/HOL                                │
│  └─ 成本: ~$500万 (按2009年学术薪资估算)                           │
│                                                                   │
│  预测: AI辅助的同等规模验证 (Kleppmann, 2025)                      │
│  ├─ 规约生成: LLM辅助 → 减少80%初稿时间                             │
│  ├─ 证明构造: AI建议tactics + 自动引理 → 减少60%证明人力             │
│  ├─ 回归验证: 全自动CI流水线 → 边际成本趋近于零                      │
│  └─ 预估总成本: 下降1-2个数量级                                     │
└──────────────────────────────────────────────────────────────────┘
```

> **Martin Kleppmann** (2025): "Formal Verification Will Go Mainstream in the Age of AI", *Conference Keynote / Technical Essay*.

**批判性分析**：Kleppmann的预测假设了AI生成证明的可靠性将持续提升，但未充分考虑"验证什么"这一元问题。形式化验证的价值取决于规范的完备性，而规范编写本质上是对问题域的深度理解——这正是当前LLM最薄弱的环节。此外，成本下降的幅度高度依赖于具体领域：协议验证（TLA+）的收益远大于操作系统内核（Isabelle/HOL），因为后者需要大量领域特定的数学引理库。预测中"1-2个数量级"的下降可能仅适用于TLA+/Dafny等高级规约语言，对于Coq/Isabelle级别的底层证明，下降空间可能仅为50-70%。

### 2.3 Vericoding vs Vibecoding：两种AI编码范式

**定义**：2025年学术界提出的概念二分法，区分了两种AI辅助编码范式：
- **Vibecoding**（氛围编程）：开发者用自然语言描述意图，LLM生成代码，依赖测试和审查保证质量
- **Vericoding**（验证编程）：开发者用自然语言描述意图，LLM生成形式化验证代码，依赖数学证明保证正确性

**工具谱系**：

```text
Vericoding工具谱系（2025-2026）
│
├─【微软生态】
│   ├─ Dafny ──→ 支持预条件/后条件/不变量的自动验证语言
│   └─ F* ─────→ 依赖类型 + SMT求解，用于加密协议验证
│
├─【Rust生态】
│   ├─ Verus ──→ Rust子集的形式化验证，已验证AWS Firecracker组件
│   └─ Prusti ─→ 基于Viper的Rust验证工具
│
├─【学术前沿】
│   ├─ Lean 4 ─→ 依赖类型 + tactic元编程，数学证明与程序验证统一
│   ├─ Rocq ───→ Coq的继任者，构造性数学与程序提取
│   └─ Isabelle/HOL ─→ 高阶逻辑，seL4等大型验证项目的基石
│
└─【工业集成】
    ├─ Nagini ─→ Python的形式化验证（JetBrains Research）
    └─ GitHub Spec Kit ─→ 自然语言→形式化规范的Copilot扩展
```

> **Academic Community** (2025): "Vericoding: Verified Coding with Large Language Models", *arXiv preprint*.

**批判性分析**：Vericoding的瓶颈不在于工具可用性，而在于认知门槛。Vibecoding的吸引力在于"快速原型"的反馈循环，而Vericoding要求开发者具备形式化思维的先验知识。当前工业实践中，Vericoding更适合"高后果失败"领域（加密、共识协议、安全关键系统），而Vibecoding在通用业务逻辑中仍占主导。两种范式并非互斥——未来可能形成"Vibe原型 → Veri加固"的两阶段开发流程。一个未被充分讨论的风险是：Vericoding工具链本身（如Dafny编译器、SMT求解器）的可靠性决定了整个验证的可靠性，而这些基础组件的形式化验证程度参差不齐。

### 2.4 端到端验证流水线：2025-2026前沿突破

#### 2.4.1 3DGen：从RFC到可证明正确的解析器

**定义**：**3DGen**（ICSE 2025）是AI驱动协议规范系统，将RFC文档中的散文描述自动翻译为3D DSL形式化规范，再通过EverParse编译为可证明正确的C/Rust解析器。

**机制**：
1. **输入**：IETF RFC文档（如DNS、TLS 1.3、QUIC）
2. **AI翻译**：LLM将RFC中的消息格式描述翻译为3D DSL（Data Description Language）
3. **形式化编译**：EverParse将3D规范编译为C/Rust代码 + 形式化正确性证明
4. **输出**：零运行时开销的经过验证的解析器

**案例**：3DGen已验证20种网络协议（包括DNS、TLS、QUIC），生成的解析器在性能和安全性上均优于手写实现。在TLS 1.3握手解析器中，3DGen自动消除了所有缓冲区溢出和整数溢出漏洞类别。

> **Microsoft Research / INRIA** (2025): "3DGen: AI-Driven Protocol Specification from RFCs to Verified Parsers", *ICSE 2025*.

**批判性分析**：3DGen的可靠性依赖于RFC文档的清晰度和LLM翻译的准确性。对于描述模糊或包含实现注释的RFC，AI翻译可能产生歧义。此外，3DGen处理的是"数据格式"层面，而非"协议状态机"层面——它保证了解析正确性，但不保证协议逻辑正确性。这意味着3DGen必须与TLA+/模型检测互补使用，才能构成完整的协议验证。

---

#### 2.4.2 ClassInvGen：LLM合成类不变量

**定义**：**ClassInvGen**（SAIV 2025）使用LLM合成面向对象程序中的类级不变量（Class Invariants），替代传统上需要为每个函数编写的函数级规范。

**机制**：
- **输入**：Java/C#类的源代码 + 自然语言文档
- **处理**：LLM分析类的字段和方法，推断"在所有公共方法执行前后都应保持"的全局约束
- **输出**：形式化类不变量（如 `∀o: Account, o.balance ≥ 0`）
- **验证**：通过Dafny/Nagini等工具验证不变量是否被所有方法保持

**案例**：在大型银行系统的Java核心模块中，ClassInvGen将需要编写的规范数量从~800个函数级规范减少到~40个类级不变量，同时保持了等价的安全保证。

> **Research Team** (2025): "ClassInvGen: LLM-Synthesized Class Invariants for Scalable Verification", *SAIV 2025*.

**批判性分析**：类不变量合成的挑战在于"过度约束"与"约束不足"之间的平衡。LLM可能生成过于严格的不变量（排除了合法状态）或过于宽松的不变量（遗漏关键属性）。当前技术仍需人类审查每个生成的不变量，且对涉及多个类之间关系的"全局不变量"处理能力有限。此外，面向对象中的继承和多态为不变量合成引入了额外的复杂性——子类可能违反父类的不变量，而LLM在这类Liskov替换原则相关推理上表现不稳定。

---

#### 2.4.3 VeriStruct：AI辅助数据结构验证

**定义**：**VeriStruct**（TACAS 2026）专门用于自动化验证Verus中的数据结构模块（链表、哈希映射、B树等）。

**机制**：
- 利用LLM生成数据结构的抽象函数（Abstraction Function）和表示不变量（Representation Invariant）
- 自动生成并验证关键操作（插入、删除、查找）的功能正确性
- 通过"证明模板"技术将常见数据结构的验证模式参数化

**案例**：VeriStruct已成功验证包含10,000+行Rust代码的复杂数据结构库，其中B树的验证时间从数人周缩短到数小时。

> **Research Team** (2026): "VeriStruct: AI-Assisted Automated Verification of Data Structures in Verus", *TACAS 2026*.

**批判性分析**：VeriStruct的自动化程度高度依赖于数据结构的"标准性"——对于常规链表、二叉树等结构表现优异，但对于使用非标准内存布局（如跳表、B+树变体）或涉及并发访问的数据结构，仍需大量人工干预。此外，Verus对Rust子集的限制意味着某些unsafe Rust代码无法被验证，这限制了其在底层系统编程中的适用性。

#### 2.4.4 Clover：闭环可验证代码生成

**定义**：**Clover**（SAIV 2024）将LLM代码生成与形式化验证器集成在反馈循环中，实现"生成-验证-修复"的自动化迭代。

**机制**：

```text
Clover闭环流程：
  自然语言需求 → LLM生成代码 → 形式化验证器检查
                          ↓
                    验证通过？──是──→ 输出验证代码
                          ↓ 否
                    反例/错误信息 → LLM修复 → 重新验证
                          ↓
                    迭代直至通过或达到最大轮数
```

**案例**：Clover在Dafny程序合成任务中，将首次通过率从~35%提升至~72%，平均需要2.3轮迭代。

> **Research Team** (2024): "Clover: Closed-Loop Verifiable Code Generation", *SAIV 2024*.

**批判性分析**：Clover的收敛性不保证——在某些情况下，LLM可能陷入"修复引入新错误"的循环。此外，反馈循环的质量取决于验证器输出的信息量：SMT求解器的反例通常难以理解，限制了LLM的修复能力。Clover在简单算法（排序、搜索）上表现良好，但在需要复杂数据结构设计或并发控制的场景中，迭代次数呈指数增长，实用性受限。

---

#### 2.4.5 Rust自动证明：自我进化的验证

**定义**：ICLR 2025发表的工作，通过"自我进化"（Self-Evolution）机制实现Rust代码的自动证明生成——LLM不仅生成证明，还通过验证失败反馈迭代改进自身的证明策略。

**机制**：
- **训练数据**：从Rust生态系统中收集已验证的crate和对应的Lean/Verus证明
- **自我进化循环**：生成证明 → 验证器检查 → 收集失败模式 → 微调模型 → 重新生成
- **关键技术**：将编译错误和证明失败信息编码为"课程学习"（Curriculum Learning）信号

**案例**：在标准库数据结构的验证任务中，自我进化模型将证明生成成功率从初始的28%提升至63%，超过了未使用进化机制的基线模型（45%）。

> **Research Team** (2025): "Self-Evolution for Automatic Proof Generation in Rust", *ICLR 2025*.

**批判性分析**：自我进化方法面临"数据墙"问题——高质量的Rust形式化证明数据相对稀缺，限制了模型的上限。此外，进化过程可能过拟合到特定验证器（如Verus）的quirks，生成的证明在迁移到其他框架（如Prusti）时可能失效。更重要的是，自我进化并未解决"规范从何处来"的根本问题——它假设规范已由人类提供，仅自动化了证明构造过程。

### 2.5 LLM用于主流程序验证：JetBrains Research

**定义**：**JetBrains Research** 2025年3月的系统性研究，评估了主流LLM（Claude 3.5 Sonnet、GPT-4等）在Dafny、Verus、Nagini等程序验证工具上的实际表现。

**核心发现**：

| 验证工具 | 目标语言 | 代表LLM | 关键发现 | 准确率估算 |
|---------|---------|---------|---------|-----------|
| **Dafny** | 类C# | Claude 3.5 Sonnet | 前置/后置条件生成取得有希望的结果 | ~65% |
| **Verus** | Rust子集 | Claude 3.5 Sonnet | 所有权相关规范生成仍需改进 | ~45% |
| **Nagini** | Python | GPT-4 | 类型注解→验证注解的翻译可行 | ~55% |

**机制**：研究团队设计了从简单到复杂的验证任务阶梯：
- **L1**：生成数组边界检查规范
- **L2**：生成循环不变量
- **L3**：生成复杂数据结构的表示不变量
- **L4**：修复验证失败的代码

> **JetBrains Research** (2025): "Can LLMs Enable Verification in Mainstream Programming?", *arXiv preprint*.

**批判性分析**：JetBrains的研究方法严谨，但其评估数据集规模有限（~200个验证任务），且主要集中在"教科书级"示例上。工业级代码库（如数百万行Python/Rust）中的验证任务涉及复杂的模块间依赖和隐式契约，当前LLM在这些场景中的表现尚不明确。此外，研究未充分评估LLM生成规范中的"隐含假设继承"问题——即LLM可能复制训练数据中的错误假设。Claude 3.5 Sonnet在Dafny上65%的准确率意味着每3个生成规范中就有1个需要修正，这在安全关键场景中仍不可接受。

### 2.6 GitHub Spec Kit：规约驱动开发

**定义**：**GitHub** 2025年推出的Copilot扩展工具链，将自然语言需求直接转化为形式化规范，驱动AI代码生成和验证。

**机制**：
1. **Spec捕获**：开发者在IDE中用结构化自然语言编写需求（类似Gherkin但带形式化语义）
2. **Spec翻译**：Copilot将需求翻译为Dafny/TLA+/Verus规范
3. **代码生成**：基于规范生成实现代码
4. **验证集成**：自动调用验证器检查代码是否满足规范
5. **反馈回路**：验证失败时，Copilot解释错误并建议修复

**案例**：在GitHub内部的微服务接口验证试点中，Spec Kit将API契约的定义时间从平均45分钟缩短到8分钟，且接口违规错误在CI阶段被拦截率提升了40%。

> **GitHub** (2025): "Spec Kit: Spec-Driven Development with GitHub Copilot", *GitHub Blog / Technical Preview*.

**批判性分析**：Spec Kit的最大风险在于"规约即代码"的新依赖层级。如果AI生成的规范本身存在语义漂移，后续所有验证都将建立在错误基础之上。此外，Spec Kit目前仅支持有限的语言和验证后端（主要面向Dafny和TLA+），对于C++、Go等主流工业语言的验证支持尚处早期。从组织角度看，Spec Kit要求开发者学习一种新的"结构化自然语言"语法来编写需求——这种学习曲线可能抵消了形式化验证带来的部分收益。

## 三、AI辅助验证的具体模式

### 3.1 从代码生成规范

```python
# 输入：Python代码
def transfer(from_acc, to_acc, amount):
    if from_acc.balance >= amount:
        from_acc.balance -= amount
        to_acc.balance += amount
        return True
    return False

# LLM生成的不变量候选：
# 1. from_acc.balance + to_acc.balance == total（全局守恒）
# 2. from_acc.balance >= 0（无透支）
# 3. amount >= 0（非负转账）

# 人类验证后转化为TLA+：
# Invariant ==
#   \A a, b \in Accounts:
#     a /= b => account[a] + account[b] = initial_total
```

### 3.2 证明策略建议

```coq
(* Coq证明中，LLM建议tactics *)

Theorem add_commutative : forall n m, n + m = m + n.
Proof.
  (* LLM建议：使用归纳法 *)
  intros n m.
  induction n as [| n' IHn'].
  - (* 基础情况：0 + m = m + 0 *)
    simpl.
    (* LLM建议：使用已证明的引理 *)
    apply add_0_r.
  - (* 归纳步骤：S n' + m = m + S n' *)
    simpl.
    (* LLM建议：重写使用归纳假设 *)
    rewrite IHn'.
    (* LLM建议：对称性 *)
    symmetry.
    apply add_succ_r.
Qed.
```

## 九、形式化定义

```
AI辅助验证管道的形式化模型：

  Pipeline = (SpecGen, ProofAssist, Verify, Feedback)

  SpecGen: Code × NL → CandidateSpec
    （从代码和自然语言生成候选规范）

  ProofAssist: Goal × Context → TacticSequence
    （从证明目标和上下文建议证明策略）

  Verify: Spec × Implementation → {Valid, Invalid(CE), Timeout}
    （验证规范是否被实现满足，返回有效/反例/超时）

  Feedback: CE × Context → Explanation × Fix
    （从反例和上下文生成解释与修复建议）

可靠性条件：
  ∀s ∈ SpecGen output: Verify(s, Impl) = Valid ⟹ s语义正确

  注意：SpecGen本身不可信，必须经过Verify的过滤。
```

## 十一、批判性总结

AI辅助形式化验证的热度需要冷静的审视，而2025-2026年的前沿进展既带来了希望也暴露了新的结构性挑战。当前端到端验证流水线（3DGen、ClassInvGen、VeriStruct等）仍局限于特定领域——协议解析、标准数据结构、教学示例——尚未覆盖通用业务逻辑。JetBrains研究显示Claude 3.5在Dafny上仅65%的准确率、Verus上45%的准确率表明，"人类审查"环节在短期内不可移除，每3个生成规范中就有1个需要修正，这在安全关键场景中仍不可接受。

核心风险已从单纯的"规范漂移"升级为"元意图"问题：当需求本身模糊或冲突时，无论AI多么强大，形式化规范都无法自动生成。Kleppmann预测的"成本下降1-2个数量级"可能仅适用于TLA+/Dafny等高级规约语言，对于Coq/Isabelle级别的底层证明，下降空间可能仅为50-70%。Vericoding与Vibecoding的二分法揭示了一个更深层的事实——形式化验证的认知门槛并未因AI而消失，只是从"写证明"转移到了"审规范"。

与纯人工形式化相比，AI辅助降低了规约编写成本但引入了工具链可靠性风险：Vericoding工具链本身（Dafny编译器、SMT求解器、Verus验证器）的形式化验证程度参差不齐，这些"验证器的验证"问题尚未解决。与全自动程序合成相比，当前技术远未达到"给定规约即得正确实现"的水平——Clover的反馈循环可能陷入"修复引入新错误"的循环，Rust自动证明的自我进化面临数据墙和过拟合问题。

未来5-10年的关键突破点可能在于：Intent Formalization的L3级DSL自动综合、Neural Theorem Prover与符号验证引擎的深度融合、不变量合成的神经-符号混合方法，以及形式化规约作为LLM微调的专业语料库。但无论技术如何进步，"验证什么"的决策权将始终属于人类——因为形式化验证的价值取决于规范的完备性，而完备性是对需求的理解，不是计算问题。形式化验证的精确性只能保证"模型内的正确性"，而模型边界的确定将永远是人类的专属领地。

## 十四、形式化推理链：AI辅助验证管道的可靠性条件

> **权威来源**：Leslie Lamport (2002); Emily First et al. (2023) "Baldur"; Albert Q. Jiang et al. (2022) "Draft, Sketch, and Prove"

### 14.1 AI辅助验证管道的形式化模型

```
定义（AI辅助验证管道）：Pipeline = (SpecGen, HumanReview, Verify, Feedback)

  SpecGen: NL × Code → CandidateSpec
    （从自然语言需求和代码生成候选规约）

  HumanReview: CandidateSpec → ApprovedSpec ∪ RejectedSpec
    （人类专家审查语义正确性）

  Verify: ApprovedSpec × Implementation → {Valid, Invalid(CE), Timeout}
    （形式化后端验证）

  Feedback: CE × Context → Explanation × FixSuggestion
    （从反例生成解释和修复建议）

定理（管道可靠性——必要条件）：
  若 ∀s ∈ ApprovedSpec: Verify(s, Impl) = Valid ⟹ s 语义正确，
  则管道是可靠的。

证明（由Verify的定义直接可得）：
  Verify的后端（TLC/Coq/Z3）是数学严格的。
  若Verify = Valid，则 ApprovedSpec 被实现满足。

  但关键风险在于 HumanReview：
    若 HumanReview 通过了语义错误的 CandidateSpec，
    则 Verify 只能证明"实现符合错误规约"，
    无法证明"规约符合真实意图"。

  ∴ 可靠性依赖于 HumanReview 的完备性，而这是不可自动化的。

定理（规范漂移的不可消除性）：
  在通用问题域中，不存在算法可判定 CandidateSpec 是否精确捕获自然语言意图。

证明概要（由Rice定理推论）：
  规约语义等价性是不可判定的。
  LLM生成的候选规约与真实意图的语义等价性，
  可归约到程序等价性问题，而程序等价性是不可判定的。
  ∴ 规范漂移无法被完全自动化消除，必须保留人类审查环节。
```

### 14.2 LLM生成规约的统计保证边界

```
定义（生成准确率）：
  P(correct | LLM(NL)) = 语法正确率 × 语义正确率

当前经验估计（2024-2026文献）：
  - TLA+语法正确率：~85-90%（LLM对形式化语法学习充分）
  - TLA+语义正确率：~60-70%（隐含假设/边界条件易遗漏）
  - 不变式识别率：~40-50%（Safety属性需深度领域洞察）
  - 证明策略建议准确率：~70-80%（简单归纳/案例分析可用）

定理（人机协作的最优策略）：
  设人类审查成本为 C_h，LLM生成成本为 C_l（C_l << C_h）。
  设遗漏错误成本为 C_e（可能极高）。

  最优策略：
    - 用LLM生成大量候选（低成本扩展）
    - 人类审查聚焦于：Safety不变式 + 边界条件 + 隐含假设
    - 机器验证过滤所有语法/逻辑错误

  期望成本：E[Cost] = n·C_l + C_h + P(error|HumanReview)·C_e

  当 C_h 足够小（LLM辅助降低审查时间），且 P(error|HumanReview) 足够低时，
  人机协作的期望成本远低于纯人工或纯AI方案。
```

```text
│   │       └─ 结果分析：
│   │             ├─ Valid → 人类确认规约语义，结束
│   │             ├─ Invalid(CE) → LLM辅助解释反例
│   │             └─ Timeout → 评估状态空间/证明复杂度
│   └─ 修复迭代阶段 → LLM建议修复 + 人类决策
│           └─ 修复类型：
│                 ├─ 规约错误 → 修改Spec，重新验证
│                 ├─ 实现错误 → 修改代码，重新验证
│                 └─ 抽象过度 → 细化模型，平衡复杂度
│
├─ LLM能力边界评估：
│   ├─ 语法生成 → 高信任（可编译检查）
│   ├─ 简单不变式 → 中信任（需人工验证）
│   ├─ 复杂时序属性 → 低信任（必须由人类定义）
│   ├─ 证明策略建议 → 中信任（简单场景可用）
│   └─ 反例解释 → 中高信任（格式化输出可靠，深层分析需人工）
│
└─ 风险缓解策略：
    ├─ 规范漂移 → 双人审查 + 领域专家终审
    ├─ 隐含假设 → 显式文档化所有假设，评审 checklist
    ├─ Selfie漏洞 → 独立安全审计，不依赖单一规约源
    └─ 归纳失败 → 多角度验证（模型检测+定理证明+测试）
```

## 十六、国际课程对齐标注

> **国际课程对齐**:
>
> - **CMU 15-317 Constructive Logic**: AI生成规约的"规范漂移"问题对应构造性逻辑中的"证明正确性"（Proof Correctness）——证明的结构正确不等于命题的真实意图被捕获。
> - **Stanford CS 259 Formal Methods**: AI辅助定理证明（如Baldur/Draft-Sketch-Prove）是本课程"自动化推理"（Automated Reasoning）的前沿方向；SMT求解器作为LLM验证后端是"神经-符号融合"的实践。
> - **MIT 6.858 Security**: "Selfie漏洞"（形式化证明中的隐含假设盲区）映射到安全课程中的"威胁建模完整性"——攻击面分析必须独立于验证工具本身。
> - **Team Topologies (Skelton & Pais, 2019)**: AI辅助形式化验证团队可定位为新型Enabling Team，通过生成规约模板和解释验证结果，降低Stream-aligned Team使用形式化方法的认知负载。
